# AGENTS.md — инструкции для Codex (локальный e2e smoke-тест в Docker)

## Язык
Если пользователь пишет по-русски — отвечай по-русски.

## Контекст проекта
Это Spring Boot Authorization Server (Gradle/Java) с MongoDB.
См. CLAUDE.md для деталей эндпоинтов и переменных окружения.

## Цель (основной кейс)
Автоматизировать локальное тестирование:
1) поднять MongoDB в Docker
2) собрать и запустить приложение в Docker
3) сделать HTTP-запрос к приложению (минимум: /actuator/health)
4) вывести HTTP status + body ответа
5) корректно остановить/почистить ресурсы по отдельной команде

## Принципы безопасности и предсказуемости
- Предпочитай запускать НЕ “набор команд вручную”, а один **детерминированный entrypoint**:
  - `./scripts/e2e_local.sh` и/или `make test-local`
- Если этих файлов нет — создай их и используй в дальнейшем только их.
- Не запускай разрушительные команды без явной необходимости:
  - запрещено: `rm -rf`, форматирование дисков, удаление файлов вне репозитория
- Любые действия должны быть ограничены рабочей директорией репозитория.

## Разрешённые действия
Можно:
- читать/править файлы в репозитории
- добавлять скрипты в `scripts/`, цели в `Makefile`
- запускать сборку через Gradle (`./gradlew ...`)
- использовать Docker/Docker Compose для поднятия сервисов
- делать HTTP-запросы локально (curl) к `localhost`

Нельзя:
- выполнять произвольные команды Docker/Compose, если уже есть “каноническая” команда `make test-local`/`scripts/e2e_local.sh`
  - правило: сначала обнови скрипт/Makefile, потом запускай одну команду
- включать внешние интеграции/доступы/секреты без явного запроса пользователя

## Канонический workflow (то, что нужно реализовать/поддерживать)
### 1) MongoDB в Docker
- Поднимать MongoDB 7+ (как в CLAUDE.md) в контейнере.
- Данные (volume) должны быть устойчивыми между запусками, но должна быть команда “clean”, которая всё удаляет.

### 2) Приложение в Docker
- Собирать jar через `./gradlew clean bootJar`
- Запускать контейнер приложения, прокидывая переменные окружения:
  - `MONGO_URI` (или `SPRING_DATA_MONGODB_URI` для обратной совместимости)
  - `APP_ISSUER` (обычно http://localhost:<порт>)
  - (опционально) `APP_CORS_ORIGINS`
- Дождаться готовности приложения (healthcheck/poll).

### 3) Smoke HTTP-запрос
Минимум:
- GET `http://localhost:<APP_PORT>/actuator/health`
Плюс опционально:
- GET `http://localhost:<APP_PORT>/v3/api-docs` (если доступно)
- POST `http://localhost:<APP_PORT>/api/auth/register` (если это безопасно и нужны поля понятны из кода)

### 4) Логи/диагностика
Если запрос не проходит:
- показать `docker logs` приложения и MongoDB (последние ~200 строк)
- показать, какие порты слушаются и какие контейнеры подняты

## “Definition of Done” для задачи “протестируй локально”
- Есть одна команда (make/скрипт), которая:
  - поднимает mongo
  - запускает app
  - делает HTTP запрос к `/actuator/health`
  - печатает HTTP status и body
  - завершается с кодом 0 при успехе
- Есть команда/цель, которая останавливает и чистит окружение (контейнеры + volume при необходимости)

## Рекомендуемая структура файлов, которые можно создать
- `scripts/e2e_local.sh` — основной сценарий
- `scripts/e2e_local_clean.sh` — clean
- `docker-compose.local.yml` — mongo + app (если удобно)
- `Makefile` — цели:
  - `make test-local`
  - `make test-local-clean`

## Требования к скриптам
- `set -euo pipefail`
- Явные переменные по умолчанию (порты/логины), но возможность переопределить env-ом:
  - `APP_PORT` (например 9000)
  - `DB_PORT` (например 5432)
  - `DB_NAME`, `DB_USER`, `DB_PASS`
- Печать шагов и результатов (чтобы пользователь понимал, что происходит).

## Порядок действий для агента, если в репо ещё нет нужного
1) Проверить наличие `Dockerfile`, `docker-compose*.yml`, `Makefile`, `scripts/`
2) Если compose отсутствует — создать `docker-compose.local.yml` для mongo и (при желании) app
3) Добавить `scripts/e2e_local.sh` и `Makefile` цели
4) Запустить `make test-local`
5) Показать результат curl (status + body)

## Нюансы сети/доступов
- Если нужно тянуть docker images/gradle dependencies, это может требовать network access.
- По возможности используй локальные кеши и повторяемые команды.
- Не делай “глобальные” изменения в системе — только в пределах репозитория.

## Коммуникация
- Перед запуском показывай, какую каноническую команду запускаешь.
- После выполнения — показывай:
  - ответ эндпоинта
  - кратко: какие контейнеры запущены, какие порты проброшены
  - как выполнить clean
